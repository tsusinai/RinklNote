## 1. 已落地改动

### 1.1 账单列表 LazyColumn key / contentType（复用效率）

- `ui/screen/bookkeeping/BookkeepingScreen.kt`：主页账单列表全部 item 补 `contentType`
  （`header / summary / chart / spacer / day-card` 五类回收桶）；原先无 key 的「合计栏」
  item 补 `key = "summary"`，日卡片沿用稳定的 `key = date`（日期为分组键，天然稳定）。
- `ui/screen/bookkeeping/MonthDetailOverlay.kt`：月度明细列表全部 item 补 `contentType`
  （`header / chart / banner / category-card`）。
- 效果：LazyColumn 重组/滚动复用只比对同 contentType 项，异构 item（横幅 vs 日卡 vs 间隔）
  不再互相错位复用，减少不必要重组；key 稳定后月切换/账单增删时只重建受影响项。

### 1.2 Room 索引复核（Room v17 → v18）

复核 `BillDao` 全部查询的 WHERE / ORDER BY 与既有索引（date、server_id 唯一、category_id、
account_id）匹配情况，结论：

- **缺口**：几乎所有查询都以 `deleted = 0` 打头，列表与统计查询再按 `date` 范围/排序
  （`observeAll` / `observeByMonth` / `observeDailySpendStats` / `getBillsByDay` 等），
  单列 `date` 索引无法覆盖「软删过滤 + 日期序」的组合 → 全表扫描 + 排序。
- **动作**：新增复合索引 `(deleted, date)`（`MIGRATION_17_18`，只加索引不动列；
  schema json 已落 `app/schemas/…/18.json`）。
  列表/统计查询可沿索引序直接扫描（倒序走索引），免去显式排序与逐行 deleted 过滤；
  写入侧多维护一个索引，个人账本量级（万级以下）下插入开销可忽略。
- **不改**：`server_id IS NULL OR dirty = 1`（getUnsynced）的 OR 条件无法有效走索引，
  该查询仅同步时低频调用，保持现状；`server_id` 唯一索引已覆盖 `getByServerId` /
  `deleteByServerId`。

## 2. baseline profile 降级说明（未做，原因如下）

按计划「若工程复杂度可控则做，否则降级并记录原因」，本次**降级不做**，理由：

1. **生成强依赖设备/模拟器**：AGP `baselineprofile` 插件 + 新建 `:baselineprofile`
   macrobenchmark 模块，`generateBaselineProfile` 必须在真机/模拟器上跑 UI 遍历才能产出
   `baseline-prof.txt`——本环境无设备，产出的规则无法验证，属于「伪交付」。
2. **工程改动面大**：新增 Gradle 模块 + 版本目录条目（`androidx.profileinstaller`、
   macrobenchmark 依赖）+ CI 思路，收益却集中在冷启动首帧（本 App 冷启动大头是 Room
   种子与 Compose 首帧，列表滚动收益有限）。
3. **替代方案已覆盖主要可离线验证项**：见 §1。

**后续真机可用时的实施清单**：新建 `:baselineprofile` 模块（版本目录加
`androidx-benchmark-macro-junit4` / `androidx-profileinstaller`）→
`./gradlew :app:generateBaselineProfile`（遍历记账页滚动 + 快速记账打开）→
产物纳入版本管理。
