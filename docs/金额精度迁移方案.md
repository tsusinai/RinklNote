# 金额精度迁移方案（Double → 整数分）

> 状态：提案（未实施）。目标：消除金额在**存储、传输、计算**三层的浮点位数偏移（如 57.970000000000006）。
> 关联债务条目：AGENTS.md「已知债务」第 2 条；`server/services/Money.kt` 注释。

## 1. 问题与根因

金额全程用二进制浮点（`Double`）表示，三层都有偏移风险：

| 层 | 现状 | 风险 |
|---|---|---|
| App 存储 | `bills.amount` / `budgets.amount` / `bill_templates.amount` 均 `Double`（Room REAL） | SUM 聚合漂移；相等比较误判 |
| 传输 | DTO 全 `Double`（App `DTOs.kt` 10 处、Server 路由、Web `types.ts`） | 序列化往返放大误差；LWW 同步时「同额」被误判为不同 |
| 计算 | 输入路径 `String.toDouble()` 后直接落库（`QuickAddViewModel` 等） | 0.1 + 0.2 类误差从源头进入 |
| Server | DB 列 `double`（4 张表），出口处 `Money.cents()` 四舍五入 | 只治显示不治存储；DB 内 SUM / 预算比较仍是浮点 |

服务端 `Money` 注释里已写明这是「backward compatibility」的妥协——本方案就是还掉这笔债。

## 2. 目标与非目标

**目标**
1. 金额在三层的事实源统一为**整数分**（`Long`，单位 minor unit）。
2. 旧数据无损迁移（含 57.97 这类经典漂移值）。
3. 新旧客户端与服务端可共存过渡（已发布的旧 App 不被破坏）。

**非目标**
- 多币种支持（仍单币种 CNY）。
- 修复「旧数据本身因浮点已经四舍五入错 1 分」的历史脏数据——迁移时按「最接近的 2 位小数」取值，不追溯。
- 顺手改 `fallbackToDestructiveMigration`（另一条债务，另行处理）。

## 3. 方案选型

| | A. 整数分 `Long`（推荐） | B. `DECIMAL/NUMERIC(12,2)` + BigDecimal | C. 维持 Double + 全出口四舍五入 |
|---|---|---|---|
| 存储精度 | ✅ 精确 | ✅ 精确 | ❌ 存储仍漂 |
| Room 适配 | ✅ 原生 INTEGER | ⚠️ 需 TypeConverter 存 TEXT，SQL SUM 失效 | ✅ |
| JSON 协议 | ✅ 整数，JS number 精确（<2^53） | ⚠️ 需自定义 serializer，字符串/对象争议 | ⚠️ |
| SUM/比较 | ✅ SQL 直算 | ✅ | ❌ |
| 改动面 | 大（但一次到位） | 大且更别扭 | 小 |
| 敏感范围 | 9e13 万元（2^53 分） | 任意 | — |

**结论：A。** 个人记账金额远小于 2^53 分，整数分在 Kotlin/PostgreSQL/SQLite/JS（number）全链路都是精确整数运算；BigDecimal 在 Room 和 JSON 两端都要打洞，收益不成比例。C 只是把现有 `Money.cents()` 的思路推到客户端，治标不治本，可作为**止血项先行**（见 §9）。

## 4. 数据模型变更

### 4.1 App（Room v12 → v13）

实体改造（3 张表同样处理）：

```kotlin
// Bill.kt / Budget.kt / BillTemplate.kt
val amountMinor: Long   // 单位：分。列名与旧 amount 区分，避免亲和性冲突
```

> SQLite 不支持直接 ALTER 列类型，且 Room 的 TableInfo 校验 REAL ≠ INTEGER。采用**新表重建**（Room 官方改列类型的标准做法）：

`MIGRATION_12_13`（以 bills 为例，budgets / bill_templates 同理）：

```sql
CREATE TABLE IF NOT EXISTS bills_new (
  id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  amountMinor INTEGER NOT NULL,
  -- ... 其余列照抄现有 schema，仅 amount REAL → amountMinor INTEGER
);
INSERT INTO bills_new (...)
  SELECT id, CAST(ROUND(amount * 100) AS INTEGER), ... FROM bills;
DROP TABLE bills;
ALTER TABLE bills_new RENAME TO bills;
CREATE INDEX index_bills_category_id ON bills(category_id);
CREATE INDEX index_bills_account_id ON bills(account_id);
CREATE INDEX index_bills_date ON bills(date);
CREATE UNIQUE INDEX index_bills_server_id ON bills(server_id);
```

注意：
- 外键引用的是 categories / accounts（无表引用 bills），重建顺序安全；仍建议迁移中 `PRAGMA foreign_key=OFF` → 迁移 → `PRAGMA foreign_key_check`。
- 索引必须手动重建（@Entity 里声明的索引 Room 不会在迁移中补建）。
- **`fallbackToDestructiveMigration` 兜底仍在**：迁移写错 = 静默清库，迁移测试是硬要求（§8）。
- `exportSchema = true` 落 `app/schemas/13.json`。

### 4.2 Server（Exposed + PostgreSQL）

表定义：`double("amount")` → `long("amount_minor")`（4 张表：bills / budgets / bill_templates / accounts.balance）。

迁移走 `plugins/Database.kt` 现成的幂等 ALTER 基建：

```sql
ALTER TABLE bills ADD COLUMN IF NOT EXISTS amount_minor BIGINT;
UPDATE bills SET amount_minor = CAST(ROUND(amount * 100) AS BIGINT) WHERE amount_minor IS NULL;
-- 过渡期双列并存（回填后设 NOT NULL 也可，见 §7 步骤 4 再收紧）
```

### 4.3 Web

`types.ts` / `api/*.ts` 中 `amount: number` 语义改为「分」→ 重命名 `amountMinor: number`（JS number 对 <2^53 整数精确）。**不允许**在 Web 内部出现「元的 number」参与运算；所有 `/100` 只发生在显示格式化层。

## 5. API 协议迁移（兼容是关键）

服务端 DTO **双字段过渡**，而不是改类型：

```kotlin
data class BillDto(
    @SerialName("amountMinor") val amountMinor: Long,          // 新：分，唯一事实源
    @SerialName("amount") val amountLegacy: Double? = null,    // 旧：元，服务端换算输出，只读
)
```

规则：
- **写**（POST/PUT）：服务端优先取 `amountMinor`；缺失时回退解析旧 `amount`（`Money.toMinor(legacy)`）。
- **读**（GET）：`amountMinor` 必出；`amountLegacy = amountMinor / 100.0` 仅为旧客户端兜底（该 double 不精确，但旧客户端本来就活在浮点世界，不劣化）。
- **同步**：`SyncManager` 上行改带 `amountMinor`；`server_id` 去重与 `base_updated_at` 乐观锁逻辑不变——冲突判定基于 `updatedAt`，与金额表示无关，**LWW 语义零改动**。
- 洞察/日报/QQ Bot 等服务端聚合：`SUM(amount_minor)` 直接整数求和，`Money.cents()` 从「止血」降级为「兼容输出换算」。

## 6. App 内部改造清单（扫描结果）

| 位置 | 改法 |
|---|---|
| `QuickAddViewModel`（输入核心） | `String.toDouble()` → `parseMoneyToMinor(str): Long?`（BigDecimal 解析，最多 2 位小数，`movePointRight(2).longValueExact()`）|
| `BookingOrchestrator`、`BillEditOverlay`、`BillCard`、`PlanScreen`、`BalanceEditDialog` | 金额改 Long 分；显示统一走 `MoneyFmt.formatMinor(cents)`（BigDecimal(cents, 2)，**禁止** `cents / 100.0` 再格式化）|
| `BookkeepingMonthState` / `BudgetViewModel` / `MonthlyChart` | totals、预算比较全用 Long 求和/比较 |
| `BillRepository.observeTotalExpense/Income` | `Flow<Long>`；DAO 的 SUM 直接对 INTEGER 列精确 |
| `VoiceInputUtil` / `VoiceParser` | 语音解析出的金额字符串同样过 `parseMoneyToMinor` |
| DTOs.kt 10 处 | 同 §5：新客户端只读写 `amountMinor` |

## 7. 实施步骤（每步独立可合入、可回滚）

1. **止血（可选先行）**：App 侧引入 `MoneyFmt`，所有落库前 `setScale(2, HALF_UP)`，所有显示前格式化。半天工作量，先消掉用户可见的 `57.970000000000006`。
2. **Server 双列 + 双字段**：加 `amount_minor` 列、回填、DTO 双字段、写路径优先 minor。旧客户端零感知。跑 server 测试（H2）。
3. **App 迁移 v12→13 + 全链路改分**：实体/DAO/迁移/VM/UI/同步改 `amountMinor`，上行协议切新字段。配迁移测试。这是最大的一步（估 1~1.5 天）。
4. **Web 切换**：types/api/组件改分 + `formatMoney(cents)`，Vitest 补格式化与聚合用例。
5. **收尾**（观察 1~2 个发布周期后）：服务端删 `amount` 旧列与 `amountLegacy` 字段；App 侧因走重建表，v13 起已无旧列；下线 `Money.cents()` 兼容用途。

## 8. 测试计划（对应 AGENTS.md 硬性约定 4）

- **App**
  - `MigrationTest`（MigrationTestHelper，12→13）：含漂移样本 `57.97`、负数、0、超大值（如 999999.99）、`bill_templates`/`budgets` 两表同测；迁移后外键完整性检查。
  - `parseMoneyToMinor` / `MoneyFmt` 单测：`"0.1"`→10、`"57.975"` 舍入策略、空穿/多小数位拒绝、负数。
  - `BookkeepingViewModelTest` / `QuickAddViewModelTest` 现有用例改断言为分。
- **Server**：H2 上跑迁移 + `amountMinor` 回读一致性；`InsightService` 聚合用例断言整数和（注意隐私 NFR：LLM 上下文仍是聚合，不受影响）。
- **Web**：`chartData.test` 等断言改分；新增「元↔分」显示格式化用例。

## 9. 风险与回滚

| 风险 | 缓解 |
|---|---|
| Room 迁移写错 + `fallbackToDestructiveMigration` → 清库 | 迁移测试硬门禁；上线前真机导出库实测一遍迁移 |
| 重建 bills 表丢索引/触发器 | 索引清单以 13.json 为准逐条 CREATE；本项目无自定义触发器（已核实 schema 由 @Entity 声明）|
| 旧 App ↔ 新协议窗口期数据不一致 | 服务端双字段设计：旧客户端读写旧字段（浮点，现状精度），新客户端读写 minor；二者经服务端换算桥接，不直接互写 |
| 回滚 | 步骤 2（服务端加列）天然可逆（新列可弃）；步骤 3 若需回滚，App 回退到 v12 APK + 服务端旧字段仍在 → 数据不丢（新记的账以 minor 为准换算回元）|
| 0.5 分舍入争议（如 57.975） | 统一 HALF_UP（与现有 `Money.cents` 一致），写入文档固定 |
