| 是否需要换引擎 | **现在不换**。优先做两件零成本事：真机验证 + 预离线模型检测与用户提示；sherpa-onnx 作为 Plan B，触发条件见 §6 |
| 建议的唯一代码改动 | 识别 Intent 加 `RecognizerIntent.EXTRA_PREFER_OFFLINE = true`（一行，待真机确认不劣化在线体验后再上） |

## 2. 现状梳理（代码链路，2026-09-18 核对）

- 入口：`ui/component/VoiceInputBar.kt` → `SpeechRecognizer.createSpeechRecognizer(context)`（**默认识别 Intent，未设 `EXTRA_PREFER_OFFLINE`**），实时出 partial 文本；
- 本地解析：转写文本交 `util/VoiceParser`（金额 + 分类关键词，纯本地规则）做实时预览，**解析环节本就 100% 离线**；
- 音频兜底：`util/VoiceRecorder` 并行录 AAC/M4A 到 cache；设备识别器 `onError` / 空结果时上传 `POST /api/bills/transcribe`（服务端 Whisper，`ASR_API_KEY` 配置后才可用），用完即删；
- 权限：`RECORD_AUDIO` 运行时权限已在 `AppNavigation` 处理。

关键事实：**语音记账的「智能」分两段——识别（ASR）与理解（VoiceParser/服务端 NLU）。理解段完全离线可用；离线能力短板只在识别段。**

## 3. SpeechRecognizer 离线能力分析

`android.speech.SpeechRecognizer` 是系统识别服务的壳，离线与否**取决于设备上实现该服务的 App**（Google 应用 / Gboard / OEM 私有引擎），App 无法直接控制：

1. **Google 系（Pixel、三星、小米国际版等带 GMS）**：Google 应用自带英文离线包，中文离线包通常需在「Google 应用 → 设置 → 语音 → 离线语音识别」手动下载；下载后飞行模式可用，识别质量略降（多为 2019+ 神经网络模型，中文可用性尚可）。
2. **国产 OEM（MIUI/HarmonyOS/ColorOS 等）**：多用自己的语音引擎（讯飞/自研），离线中文能力普遍**好于** Google 系（讯飞离线包成熟），但 API 行为有差异：部分机型不支持 `EXTRA_PREFER_OFFLINE`、部分不支持 partial results。
3. **`EXTRA_PREFER_OFFLINE`（API 23+）**：语义是「偏好离线引擎」，**不是保证**：Google 实现会优先用已下载的离线包；OEM 可能忽略。副作用：在线时也可能被切到离线模型，质量略降。
4. **Android 13+** 的 `createOnDeviceSpeechRecognizer`：声明「纯端上」的识别器，但仅 Pixel/部分机型有实现，**不可作通用方案**，可作为检测后的升级路径（识别器不存在时回落现有 createSpeechRecognizer）。
5. **服务端 Whisper 回落**：离线时该回落必然失败（网络不通），现有 UI 会进入错误态——这是**正确行为**，但应在「离线语音」说明里告知用户。

**预期结论（待真机确认）**：主流国产机上飞行模式语音记账「大概率直接可用」；GMS 机需用户先下载中文离线包——失败模式是 `onError(ERROR_NO_MATCH/ERROR_SERVER)` 走回落然后报错，体验可接受。

## 4. sherpa-onnx 方案对比

[sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)（k2-fsa 生态，Apache-2.0）：kotlin API + 预编译 AAR，端上流式 ASR。

| 维度 | 系统 SpeechRecognizer | sherpa-onnx（streaming zipformer / paraformer-zh / SenseVoice） |
|---|---|---|
| 离线 | 视机型/离线包 | **100% 端上，无机型差异** |
| 中文流式识别 | 稳定性视引擎 | 成熟（streaming zipformer bilingual zh-en RTF<0.1，中端机实时） |
| 实时 partial | 大多有 | 有（streaming 系列） |
| 包体代价 | 0 | bundled AAR + 模型 ≈ **+40~80MB**；或「首启下载模型」≈ 模型 20~80MB + 下载/校验/目录管理 + 失败重试 UX |
| 接入成本 | 0 | 新依赖进 `libs.versions.toml`；`VoiceInputBar` 抽一层识别器接口（系统/端上二选一）；麦克风 PCM 直喂（需放弃 MediaRecorder 通路改 AudioRecord，或走文件后整段非流式） |
| 金额识别适配 | 数字读法依赖引擎 | 同样是文本输出，`VoiceParser` 的中文数字规则完全复用 |
| 维护 | 系统，零成本 | 模型升级/版本跟进自理 |

**判断**：sherpa-onnx 的收益是「消除机型差异」，成本主要是包体与双引擎维护。在「语音记账」这个低频入口上，先用系统识别器 + 引导下载离线包的方案覆盖绝大多数场景，不划算现在就引。触发条件（满足其一再上）：① 真机矩阵验证发现 ≥1/3 主流机型离线不可用；② 用户实际反馈离线记账失败集中在识别段；③ 产品决定做「完全离线」卖点。

## 5. 其他候选简评（为什么不选）

- **Vosk**：同样端上方案，Java API 成熟但模型/工程活跃度已被 sherpa-onnx 全面替代，中文流式质量不如 k2-fsa 系，不选。
- **whisper.cpp**：识别质量高但**非流式**（说完才出结果），与现有「边说边出预览」的交互冲突，且包体/耗时更高，不选。
- **ML Kit 语音**：无中文 ASR 产品（本仓库已用其 OCR，勿混淆），不存在该选项。

## 6. 决策与最小改动清单

1. **本任务不改代码**（原计划允许「最小改动或不改」）。理由：唯一值得上的改动是 `EXTRA_PREFER_OFFLINE = true`，但它会改变在线设备上的现有行为（可能切到离线模型导致质量下降），在真机验证前贸然上线与「以实际测试结果为准」的仓库约定冲突。
2. **真机验证通过后的落地清单**（一行代码 + 文案）：
   - `VoiceInputBar` 识别 Intent 增加 `putExtra(RecognizerIntent.EXTRA_PREFER_OFFLINE, true)`；
   - 设置页/语音条说明补「离线语音：需在系统语音设置下载离线识别包」提示；
   - （可选）`SpeechRecognizer.isRecognitionAvailable()` 检测给空态提示。
3. **sherpa-onnx 立项条件**：见 §4 判断，届时再走 `libs.versions.toml` 版本目录流程。
